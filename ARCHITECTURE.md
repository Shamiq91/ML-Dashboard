# Architecture

- **Session state.** `SessionStore` (app/state/session_store.py) is the only holder of mutable pipeline state: per session the raw DataFrame, the working (cleaned) DataFrame, target, trained results, telemetry curves, jobs and a log deque. Sessions expire after 2 h idle; a background task purges them and `get()` also rejects expired ids (404).
- **Stage guard.** UPLOADED -> TARGET_SET -> CLEANED -> TRAINED. Out-of-order calls return 409 `STAGE_CONFLICT`; training additionally returns 409 `NAN_REMAINING` while NaNs exist. Changing target / cleaning / resetting clears trained results.
- **Concurrency.** Each session has an `asyncio.Lock` for mutations. CPU-bound work (parsing, KNN imputation, statistical tests, training) runs via `asyncio.to_thread`. Training is a background `asyncio.Task` wrapping one worker thread; only one job per session runs at a time and one failing model is recorded in `failed_models` without aborting the rest.
- **Leak-free training.** Preprocessing (scaling, one-hot/ordinal) is a `ColumnTransformer` fit on the training rows only; class weights and SMOTE touch only training rows. Every model's final fit uses all training rows. Iterative models (MLPs, XGBoost, LightGBM, TabNet) also get a separate telemetry fit on an inner 64/16 train/validation split for their loss curves, so telemetry never sees the test set.
- **Positive class.** `modeling.prepare_dataset` encodes the positive class of a two-class target as 1 (the request's `positive_class`, else the rarer class), so every metric and curve is about it. The model lab reads the same choice from the session.
- **Radio / WebSocket.** Services call `Radio.publish(...)` from any thread; it stamps `T+MM:SS`, appends to the session log, and hands the line to the loop with `call_soon_threadsafe` into an `asyncio.Queue` drained by one broadcaster task. Sends use a per-client timeout so a dead/slow client is dropped without blocking others. On connect the last 50 lines are replayed; a heartbeat frame (`{"type":"heartbeat"}`) is sent every 25 s. Without `session_id` a client only gets server-level events.
- **Frontend.** One `useReducer` + context state feeds the leaderboard, registry and comparison legend. REST via a single `api` helper; the training job is polled every second while WebSocket lines drive the CTE blocks in real time.
- **Task kinds.** The target decides the task (`session.task`): `classification`, `regression` (a numeric target with more than 20 distinct values, or forced). Regression trains each model's regressor on a target standardised with training-row statistics only; R^2 is unchanged by that, RMSE/MAE are scaled back. 19 of the 23 catalog models have a regressor. For a categorical target the assumption panel's linear-regression checks are reported as not applicable.

## Analysis, tuning and history

- **Fitted-model memory.** After each model trains, `modeling.run_training` keeps a `FittedModel` (`services/analysis.py`): the fitted `Pipeline` (preprocessor + estimator), a sample of the training rows, the test rows and the target scaling. ROC/PR, residuals, permutation importance and SHAP all run on it lazily (in a thread, cached in `FittedModel.cache`), so training itself stays fast. Changing data, target or settings clears them with the rest of the results.
- **Tuning.** `services/tuning.py` runs an Optuna TPE search per model (declarative `SEARCH_SPACES` in `model_registry.py`) with cross-validation on the training rows only: stratified for classes, plain k-fold for regression. The default configuration is scored first and the tuned parameters are used only if a trial beats it. Preprocessing sits inside the CV pipeline, so folds never see each other's scaling or encoding. Progress reaches the UI through `JobRecord.progress` and the radio.
- **PyTorch / TabNet.** `services/torch_models.py` wraps both behind sklearn's API (`fit(X, y, eval_set=...)`, `history_`, `predict_proba`), so they tune, explain and compare like any other model. Torch is imported lazily.
- **SHAP.** Tree models use `TreeExplainer`, linear models `LinearExplainer`, everything else a sampled `KernelExplainer`. One-hot columns are summed back to their original column, so explanations read in the user's feature names. Binary single-output explainers are mirrored for the negative class.
- **Run history.** `services/runs.py` keeps datasets (fingerprint of shape, columns and leading rows, so a re-upload is the same dataset) and runs (leaderboard, split, settings, target profile, downsampled ROC/PR) in SQLite under `backend/data/`. This is the only state that survives a restart; sessions remain in memory.
- **Transforms.** `services/transforms.py` applies an atomic list of cleaning operations and records the value-changing ones as a replayable recipe for exported models. The dashboard exposes imputation plus the drops, log transforms and clips suggested in `FEATURES`; the rest is API-only. The target column cannot be transformed.
- **Cross-validation.** `services/crossval.py` refits each model's pipeline (tuned params if applied; the same class weights or SMOTE as the final fit, inside each fold) on k train/validation splits of the *training rows only* (capped at `cv_max_rows`), so the hold-out rows stay untouched. Regression CV runs on the standardised target and RMSE/MAE are scaled back. Results ride on each leaderboard row as `cv`, `cv_score`, `cv_std` and are saved with the run. `modeling.rank_results` ranks by `cv_score` when every row has one (`ranked_by: "cv"`, ties broken on the hold-out score), otherwise by the hold-out F1 / R^2 (`ranked_by: "test"`), so a board never mixes the two.
- **Feature tools.** `services/features.py` scores columns by mutual information on a sample (IDs and constants are not scored).

## Model lab

- **Stateless fits.** `services/lab.py` re-reads the session's working frame on every request (capped at `lab_max_rows`, seeded split), fits one model and returns metrics plus model-specific charts. It never writes to the session, so the dashboard's results and stage are untouched. Regression fits on a target standardised with training-row statistics; every number shown is scaled back.
- **Export.** `POST /lab/{model}/export` runs the same fit as `/fit` (shared `_fit`, same seed and split) and hands it to `services/export.py` as an `ExportSource`, so the zip, `predict.py` and model card are identical in shape to a dashboard export; the card adds the lab's hyper-parameters and settings. The dashboard export builds its `ExportSource` from the session's training run.
- **One catalog.** `services/lab_catalog.py` defines each lab model's controls (kind, range, default, help, `when` visibility, sweep values). The UI draws its controls from `GET /lab/models` and the backend validates the same definition (bad values are 400 `BAD_PARAM`; out-of-range numbers are clamped).
- **Honest diagnostics.** Linear models drop one one-hot level so coefficients are identifiable; tree thresholds are un-standardised for display and tree nodes report the real class counts of training rows (not the class-weighted shares the tree uses internally); XGBoost loss curves use an inner fit/validation split of the training rows; sweeps and learning curves cross-validate on training rows only. A sweep over a parameter that is currently inactive switches on what it needs (e.g. `gamma_mode=custom`) and reports it as `changed`.
